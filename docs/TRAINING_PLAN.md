# 训练实施计划与验收门槛

## 阶段 0：锁定模型身份

- 明确 9B GGUF 的准确文件名、来源、架构、量化类型和 SHA-256。
- 检查 GGUF metadata、tensor names/shapes/types。
- 禁止从“9B Q4”猜测模型架构；同为 9B 的模型不保证层结构、FFN 形状或 tokenizer 相同。
- GGUF 仅作为冻结推理基线；不要把它伪装成可直接用 AdamW 更新的训练权重。

## 阶段 1：建立完整路径基线

固定评测集、提示词模板、采样参数和后端版本。记录：
- 可自动验证的任务成功率/正确率；
- 首 token 延迟、生成 token/s、总耗时；
- 峰值 RSS/PSS（设备可提供时）；
- KV cache 配置、上下文长度、线程数、NPU/GPU/CPU 后端；
- 崩溃、OOM、超时和不支持的算子。

同一设备至少重复运行多次，报告中位数与高分位数，不用单次最好成绩。

## 阶段 2：采集动态预算与反事实轨迹

第一阶段先不启用结构化通道跳算。使用后端真实支持并能测量实际生效值的参数，例如上下文长度、批大小、最大生成 token、线程数、并发、停止条件和后端确实支持的 KV Cache 类型。按固定任务子集分别运行小/中/完整预算，生成同一任务的配对质量-成本曲线。

每条样本至少包含：
- 模型 SHA、后端版本、配置哈希和任务 ID；
- 预算档位、请求参数与实际生效参数；
- 任务族、数据拆分、独立质量标签及验证器；
- 首 token 延迟、总耗时、吞吐和失败原因；
- 峰值 RSS/PSS、后端缓冲区、KV Cache 观测值（可测时）；
- 回退阶段、触发原因与回退后的质量/资源结果。

同一任务不同预算必须用相同 task_id 配对；按任务族拆分 train/val/test，避免同一任务的不同预算版本泄漏到多个拆分。unknown 质量标签不能伪造成正负标签。字段规范见 [TELEMETRY_SCHEMA.md](TELEMETRY_SCHEMA.md)。

## 阶段 2B：研究结构化跳算（后续阶段）

只有在确认模型计算图和后端 kernel 能真实跳过对应计算后，才研究 FFN 通道组、层或专家级动态跳算。分组大小必须从真实 tensor shape 和 kernel 约束推导，不预设 128 通道为事实。若只是掩码模拟，必须明确标注为模拟，不能宣称有实际加速。

## 阶段 3：训练小型预算控制器

初始动作定义为经过后端能力探测的预算档位和分级回退动作，不包含尚未实现的通道跳算。第一版先用规则基线和监督学习预测：
1. 在质量门槛下可接受的预算档位；
2. 是否需要增加预算或触发资源降级；
3. 在质量门槛已满足时，是否可以停止扩容。

奖励目标采用分层约束：
- 第一层：任务质量达到门槛，否则该策略不可接受；
- 第二层：在合格策略中优化真实延迟和计算成本；
- 第三层：在质量与速度满足要求时降低峰值内存。
- 在质量门槛满足的策略之间优化实测延迟/计算成本与峰值内存；对不必要扩容施加小惩罚，对成功恢复任务的必要扩容给予奖励。
- 不将模型自身未经校准的“自信程度”当作正确性标签。

有了可靠数据后才尝试 PPO 等强化学习方法；保留固定随机种子、训练/验证/测试拆分与可恢复 checkpoint。

## 阶段 4：动态扩容与安全回退

候选池档位从小到大尝试。若客观质量检查失败、路由器不确定或出现分布外输入，则扩大候选池；到达最大预算仍无法满足门槛时，回退完整执行路径或明确返回失败。不得静默宣称成功。

## 阶段 5：证明内存和速度收益

必须分别报告：
- GGUF 文件大小；
- 进程峰值 RSS/PSS；
- NPU/后端缓冲区与共享内存（若可测）；
- 延迟、token/s、任务质量；
- 运行时是否真的跳过矩阵运算和权重读取。

mmap 本身不保证降低峰值 RAM；结构化稀疏也不保证在硬件上更快。所有结论以目标后端和目标手机的测量为准。

## 阶段 6：手机端集成

训练仓库只输出版本化路由器、分组索引和校准 manifest。Android 仓库独立实现路由执行、内存预算控制、回退和遥测。整款应用的运行时峰值必须低于 4096 MiB，并预留安全余量。


## 在线学习补充规范

训练阶段与推理阶段不必在概念上完全割裂，但必须明确区分任务内临时策略适应和跨任务持久参数更新。当前实现先采用“推理 + 独立验证 + 临时预算/路由调整 + 任务后离线训练控制器”，不在手机推理期间直接更新全局模型权重。详见 [在线学习闭环设计](ONLINE_LEARNING_LOOP.md)。
