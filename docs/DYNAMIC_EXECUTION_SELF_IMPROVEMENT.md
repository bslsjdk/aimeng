# Ornith 动态执行与自我改进架构

## 目标

把 Ornith-1.5-9B 从“固定执行的量化模型”改造成可研究、可测量、可回退的动态推理系统：根据任务难度和资源状态调整执行预算，并用可验证的结果改进调度策略。优先保持任务质量，再优化延迟、计算量与内存。

## 必须区分的三层

1. **基础模型权重**：当前固定基线为官方 `Ornith-1.5-9B-Q4_K_M.gguf`。它是量化推理工件，不等同于完整的自我改进训练代码，也不能直接假定能用常规反向传播更新。
2. **动态推理执行框架**：在兼容的推理后端中加入预算控制、动态执行策略、内存监测、结果验证和回退。只有后端真正跳过了相应运算/权重读取，才能把它计为实际计算节省。
3. **离线自我改进训练循环**：在 Colab GPU 上生成/整理任务、运行候选策略、客观评分、训练小型控制器、验证并发布新版本。训练循环更新控制器及策略参数，不应未经证据就声称它自动更新了 9B 主模型权重。

## 运行时数据流

```text
输入任务
  -> 任务/难度特征提取
  -> 资源预算控制器（延迟、可用内存、上下文、设备能力）
  -> 动态执行计划
  -> Ornith 基础模型 + 后端执行器
  -> 独立质量验证器
      -> 通过：返回结果并记录遥测
      -> 质量未通过且资源允许：增加预算重试
      -> 内存压力升高：降低并发/上下文/批大小与临时缓冲区
      -> 仍不稳定：使用已验证的保守解码配置
      -> 完整路径仅在预估资源仍安全时启用，否则明确失败
  -> 记录任务、执行计划、质量、耗时、峰值内存与回退原因
  -> 离线训练数据集
  -> 训练/验证新控制器
  -> 通过基准门槛后版本化发布
```

## 动态执行控制器

控制器输出的是受约束的执行动作，而不是任意修改模型结构：

- 当前任务使用的计算预算档位；
- 候选通道组/计算组的选择（仅当后端支持真实结构化跳算时启用）；
- 是否继续扩展候选组或上下文预算；
- 是否触发完整执行回退；
- 内存压力升高时的上下文、KV cache、并发和临时缓冲区策略。

第一版先做可解释的规则基线和监督学习控制器。只有采集到足够的真实执行轨迹、质量标签与成本测量后，才评估强化学习。禁止用伪造的节省量或模型未经校准的自信度作为奖励标签。

## 第一阶段的预算边界

第一阶段不启用未经验证的通道、神经元组或层级跳过。先只使用当前推理后端真实支持、可查询实际生效值的预算参数，例如上下文长度、批大小、最大生成 token、线程数、并发、停止条件，以及后端确实支持的 KV Cache 类型。参数能力必须在运行时探测；不支持或无法测量的功能明确标记，不得伪造执行变化。

对固定任务子集运行小/中/完整预算，形成按任务配对的质量-成本曲线。只记录单一预算的成功案例不足以判断控制器应选择哪档预算。统一字段、JSONL 示例、反事实采样和训练前数据检查见 [遥测与反事实预算数据规范](TELEMETRY_SCHEMA.md)。

## 自我改进循环

1. **任务生成**：从固定基准、失败案例和受控合成任务生成训练候选。
2. **策略探索**：在相同模型、提示模板、采样参数和硬件环境下比较不同预算/执行策略。
3. **独立评分**：优先使用单元测试、精确答案、结构校验或人工标注；无法自动判定的样本标记为未知，不强行制造标签。
4. **经验整理**：去重、分层采样、保留困难样本和失败原因，防止训练集被简单成功案例淹没。
5. **控制器训练**：训练预算选择、扩容时机与回退预测器。
6. **门槛验证**：在独立验证集和设备基准上比较新旧策略；不达标就不发布。
7. **版本回滚**：每个控制器、配置、数据快照和基准结果都有版本号；新版本表现退化时恢复上一版。

这里的“自我改进”首先指系统通过评估数据改进控制器与策略。主模型权重的继续训练属于单独项目，需要可训练的兼容权重、训练代码与相应资源，不能把 GGUF 文件本身当成完整训练管线。

## 硬约束与优化顺序

- **质量是硬门槛**：未达到质量阈值的策略不可因速度快或内存低而胜出。
- **Android 运行时内存上限：4096 MiB**。控制器必须保留安全余量；达到危险水位时先降低并发、上下文、批大小与缓存预算。PSS 3200–3400 MiB 仅作为初期测量目标，不是所有设备通用的硬阈值；应按设备校准，危险时不得盲目触发完整执行。
- **Colab GPU 显存与 Android RAM 是两个独立预算**。16 GiB GPU 可把约 14 GiB 作为规划目标并留出余量，但必须按实际可用显存自适应，绝不通过分配无用张量来“占满显存”。
- 质量门槛通过后，联合优化端到端延迟、真实计算成本与峰值内存。发布比较使用预先声明的容忍区间：质量不得退化；延迟、PSS/峰值内存、失败率和回退率一起评估，不要求每一项每次都绝对改善，也不能允许显著退化被单项收益掩盖。报告样本量与质量率置信区间。
- mmap、量化和通道掩码本身都不能证明峰值内存或延迟一定下降，必须在目标后端实测。

## 分阶段实施

### A. 可复现基线
锁定 GGUF 文件身份、后端版本、提示模板、数据集和采样参数；测量正确率、首 token 延迟、token/s、总耗时、峰值 RSS/PSS、KV cache 和失败率。

### B. 遥测与验证器
先为每次推理记录统一 schema，并实现客观评分和失败分类。缺少可靠评分的任务不得用于强化学习奖励。

### C. 动态预算原型
先实现小/中/完整预算的可解释控制和安全回退。第一版只调整后端实际支持的参数，不启用未经验证的结构化跳算。若后端尚不支持真正的结构化跳算，只能把通道选择标记为模拟实验，不宣称有实际加速。

### D. 控制器训练
用真实轨迹训练轻量路由器；固定随机种子，按任务划分训练/验证/测试集，保存 checkpoint，并与规则基线比较。

### E. 后端深度改造
根据 GGUF tensor 元数据与真实模型计算图确定可跳过的算子。任何通道分组都必须从真实形状校验得出，不能把 128 作为固定事实。先证明算子级收益，再集成控制器。

### F. 自我改进闭环
把失败样本、扩容成功案例和资源曲线回流到离线训练；新策略通过独立质量、延迟和内存门槛后才发布。

### G. Android 集成
训练仓库发布版本化控制器、配置和校准 manifest；Android 运行时仓库独立负责执行、监控、回退与 4096 MiB 硬限制。不要把训练环境依赖混进手机运行时。

## 最低验收标准

- 基线与新策略使用相同测试集和推理参数；
- 质量不低于预先定义的门槛；
- 证明动态动作改变了真实执行路径，而不是只改变日志；
- 报告中位数和高分位延迟、峰值内存、token/s、失败率及回退率；
- 新策略未通过验证时自动保留旧版本；
- Colab notebook 必须实际运行并保存日志后，才可标记 GPU 训练通过。
