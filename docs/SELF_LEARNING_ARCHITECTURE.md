# 自主学习型 AI：自有架构与运行平台的设计基线

## 0. 核心目标

AIMENG 的最终目标不是给现成大模型添加一个记忆插件，而是研究并实现一种**面向持续学习、任务相关计算和动态资源预算的 AI 架构**。模型架构、学习机制、内部状态、工件格式和运行时平台应共同设计。现有模型可暂作教师或实验基线，但不是最终架构必须兼容的限制。

“市面上没有相同的完整系统”是研发动机，不等于每个组成机制都没有先行研究。相关工作可能包括持续学习、条件计算、动态稀疏化、外部记忆、可塑性、检查点恢复和预算感知推理。我们的创新点必须通过明确的系统组合、实现与对照实验来证明。

## 1. 系统目标与验收原则

1. **持续学习**：从任务结果、奖励/验证器和反馈中更新可持久化经验；按风险与验证质量决定是否写入长期记忆；研究在稳定性和回放机制允许时更新可训练参数。不能把保存聊天记录称作模型参数学习。
2. **任务相关计算**：根据任务与当前状态分配有限工作集，选择需要的模块/计算路径。路由决策必须真实改变执行路径，而不只是输出一个 mask 或日志。
3. **动态资源管理**：在运行时预算下控制活跃模块、缓存和中间状态；释放资源后需要通过 RSS/PSS、驻留字节和峰值测量验证。调度元数据本身不算节省物理内存。
4. **状态可恢复**：区分持久知识、程序性经验、当前任务状态和临时工作区；保存版本、来源、验证状态与可恢复检查点。
5. **自主运行平台**：定义自有架构的张量/模块语义、训练检查点、部署工件、加载器、执行器、学习更新、调度器和遥测协议。先写最小可测实现，再扩展格式与后端。
6. **移动端约束**：Android 整应用峰值内存低于 4096 MiB 且留有余量是硬门槛；必须用目标设备整应用 PSS 与端到端任务验证，不得从模型文件大小推算达标。

## 2. 不把模型与格式倒置

- 训练/实验阶段先定义自己的逻辑架构和状态语义。
- 内部训练检查点服务于可恢复训练，需要保存参数、优化器状态（如适用）、随机数状态、数据/配置版本与训练步数。
- 部署工件服务于推理，可以有量化和布局转换，但必须可复现并校验输出一致性。
- 运行时容器/权重文件格式由我们的张量类型、模块粒度、加载策略、版本迁移和硬件后端决定。可以自行定义版本化二进制格式；不要过早把它变成训练算法的限制。
- 首版格式只实现必要功能：magic、版本、字节序、架构 ID、tensor dtype/shape、对齐与偏移、索引/目录、分块校验和、元数据、可选压缩/量化描述。禁止直接 pickle 不可信工件；读取前校验长度、偏移、shape 溢出和校验和。
- 自有格式不代表必须自写所有底层矩阵乘法。先将架构语义与 kernel/backend 接口分离，按实测选择 CPU/GPU/NPU 或现有计算库；以后可逐步替换后端。

## 3. 架构分层草案

### A. 常驻控制核
小型、可预测的调度状态机：接收事件，检查预算，恢复任务状态，决定唤醒哪些能力模块，处理超时/失败和安全回退。常驻核不持有整套大型权重。

### B. 受限工作集
固定槽位与字节预算，支持优先级、pin、LRU/显式释放、加载失败回退、资源生命周期和可观测计数。工作集管理必须连接真实分配/加载器才有内存效果；第一阶段原型只是 metadata，不可当作已完成动态权重加载。

### C. 任务计算模块
由实验决定模块粒度，可研究共享主干、按需激活模块、稀疏子网络、专家/技能模块或小型工作记忆。不要预先假设“神经元”是最合适的加载单元。模块粒度需权衡路由成本、局部性、缓存复用和实际算子效率。

### D. 学习与巩固
区分：
- 即时任务状态（短期、可丢弃）；
- 经验证的程序性经验（可检索、版本化）；
- 训练样本/反馈队列（带来源和验证器）；
- 参数更新（需稳定性评估、回放/正则化策略、版本和回滚）；
- 长期模型版本（通过独立评测后才晋级）。
在线更新不得在失败任务中无条件写入，避免错误反馈污染模型。

### E. 自有工件格式与加载器
训练 checkpoint 与推理工件分开。定义明确的 tensor table、模块索引、校验、映射/读取策略、版本迁移和工具。先做 Python 原型验证往返读写、损坏文件拒绝、随机张量 round-trip，再考虑 Android/Native 实现。

### F. 执行后端
统一接口包括张量运算、模块装载/卸载、缓存预算、取消、错误传播和计时。逻辑架构不应直接依赖某个文件格式或设备厂商 SDK。

## 4. 推荐实现顺序

1. **基线审计**：盘点 AIMENG 现有代码、真实训练入口、数据、测试、资源预算和已实现能力；所有状态标记为 implemented / prototype / planned。
2. **架构规范 v0**：定义模块、任务状态、学习事件、资源预算、checkpoint 与部署工件之间的边界。
3. **自有格式原型 v0**：实现安全的 tensor container writer/reader、版本号、索引、校验和、随机张量 round-trip 测试；暂不接 Android。
4. **最小可测学习体**：先用小模型/小数据验证任务反馈、经验写入、回放、参数更新与回滚的完整闭环；比较不学习、只记忆、更新参数三种基线。
5. **真实资源工作集**：从真实 tensor loader/backend 接入 load/release，测量 RSS/PSS、峰值、加载时间、token/step 延迟；没有物理资源变化就不算通过。
6. **扩展模型容量**：只有当数据、学习闭环和测量工具可靠后，才扩展参数量、模块数和训练成本。
7. **手机部署后置**：确定可用模型和推理路径后，再将运行平台移植/优化到 Android，硬门槛为整应用 PSS < 4096 MiB 并留余量。

## 5. 关键实验与对照

每个实验固定代码提交、数据 manifest/hash、模型/架构版本、随机种子、训练配置与设备。

- 学习效果：未见任务成功率、保留任务回归、样本效率、校准误差、错误写入率。
- 持续学习稳定性：新任务前后旧任务能力、回放收益、遗忘曲线、回滚正确性。
- 动态计算效果：激活模块/实际算子数量、端到端延迟、路由开销、输出质量。
- 内存效果：整进程/整应用 PSS、RSS/HWM、真实权重驻留字节、加载峰值、释放后内存变化。
- 自有格式正确性：round-trip、损坏/截断/恶意偏移拒绝、跨版本兼容、量化误差。
- 移动端效能：首 token、生成吞吐、任务完成时间、峰值 PSS、OOM/崩溃率。

所有结果要有可复现日志。单一指标提升不能代替整体质量/速度/内存的权衡。

## 6. 与现有项目的关系

- `bslsjdk/aimeng` 是当前训练与架构研究主仓库。
- `bslsjdk/ai` 是已有 Android 运行软件仓库，暂时不要求为尚未确定的自有架构进行大规模修改。
- 现有 Ornith/GGUF 实验可用于教师知识生成、行为基线和比较实验，但不等于最终架构。
- 当前 9B 教师不是自动具备本项目定义的持续参数学习与动态资源机制。知识提取和经验记忆是准备材料，不是终点。
- 两个仓库的适配工作放到自有架构形成可验证的训练/推理工件之后。

## 7. 本阶段不可声称的事项

在实际代码与实验出现之前，不声称已经实现新型通用 AI、真实在线参数学习、动态神经元卸载、自有格式可部署、手机 4 GiB 达标或性能超过现有模型。先建立最小可验证闭环，再逐项验收。
